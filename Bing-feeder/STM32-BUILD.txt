BUILDING THE SUPPLIED STM32 FEEDER PROGRAMS
=========================================
Checked 20 October 2026.

STATUS
These are four independent vendor C programs, each with its own main().
Build one variant at a time. Their source contents have not been modified.
Each program's folder contains its source and a README.md with variant details.

The supplied files are NOT complete build projects. No matching project file,
STM32F10x library, startup code, system clock implementation or linker script
was found alongside them. No build of these four programs has been verified.
The separate custom firmware under ../_other/v3-modding/ is a different program;
building that project does not build these vendor sources.

WHAT THEY USE
All four use ST's legacy STM32F10x Standard Peripheral Library (SPL), including
stm32f10x.h. This is plain C with main(), not an Arduino sketch.

ST's library package is STSW-STM32054:
https://www.st.com/en/embedded-software/stsw-stm32054.html

HOW TO GET A BUILD WORKING
1. Identify the actual feeder MCU, flash/RAM capacity and crystal frequency.
   STM32F103C8 is a candidate from the existing source/schematic audit, not a
   verified target for every board. A chip with a different marking needs its
   own confirmed memory layout and compatible library/startup files.

2. Prefer the vendor's original complete project for this exact firmware
   variant. Obtain its compiler/version, STM32F10x SPL dependency, startup
   file, system_stm32f10x.c, stm32f10x_conf.h, linker/scatter file, clock settings
   and any bootloader/application offset. This is the most direct route to
   reproducing the vendor build. A supplied .hex does not supply these files.

3. If reconstructing a project, start from a matching STM32F10x SPL template
   with the correct compiler and MCU. Keep a working copy separate from these
   preserved vendor sources. Add ONLY the selected feeder .c as the application
   main source and remove the template main(). Do not combine feeder variants.

4. Add the required SPL driver .c files listed in the variant's readme, plus
   misc.c for NVIC support. Configure include paths for the SPL driver headers,
   matching legacy CMSIS core/device headers and the project configuration.
   Supply stm32f10x_conf.h with the required peripheral headers enabled.
   Define USE_STDPERIPH_DRIVER. For a confirmed medium-density STM32F103x8/xB,
   the SPL device-class define is STM32F10X_MD; other parts need their own class.
   Keep device headers, startup and library versions compatible.

5. Include a compiler-compatible startup/vector table and system_stm32f10x.c.
   Set the actual oscillator/PLL clock and memory sizes. Preserve this source's
   interrupt handlers; do not also compile template handlers of the same names.
   Link only one SystemInit implementation. V485 also provides SysTick_Handler;
   its millisecond timing depends on SystemCoreClock matching the actual clock.

6. Build and link with the selected Arm compiler. Resolve compiler/linker
   errors in the separate working project; record any required source changes.
   Check the map file, vector table and flash/RAM usage before using the image.
   Successful compilation does not establish correct behavior on the feeder.

VS CODE / PLATFORMIO
VS Code can remain the editor. No CubeMX or HAL conversion is required.
For PlatformIO, first obtain or reconstruct a compatible STM32F1 SPL framework
setup, including its startup and linker configuration. The current official
bluepill_f103c8 board definition does NOT list SPL among its supported
frameworks. Merely setting framework = spl is not a complete build solution.
PlatformIO's general SPL support for other STM32 targets does not change that.
Do not mix legacy stm32f10x.h and modern device/framework headers blindly.

Once an actual PlatformIO project has been configured, open its folder in
VS Code, use Project Tasks > Build, or run pio run in its Core CLI terminal.
These source-only folders currently have no platformio.ini, so that command
does not yet work here. The first build may download dependencies.
For a supplied vendor GCC Makefile project, run its documented make target
from VS Code's terminal. A Keil .uvproj/.uvprojx instead needs its matching
MDK/Arm compiler setup unless the build is deliberately ported.

With a successfully linked GNU Arm ELF, optional output conversions are:
  arm-none-eabi-objcopy -O ihex firmware.elf firmware.hex
  arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
These convert an existing ELF; they do not compile the C source.

KNOWN VARIANT-SPECIFIC ISSUE
V3_feeder_12-16-24mm.c defines FLASH_ADDR as 0x08010100. That address is outside
the documented 64 KB flash range of an STM32F103C8 (0x08000000..0x0800FFFF).
Confirm the actual MCU and reserve the correct erase page in the memory layout
before using this persistence code. Do not silently assume 128 KB, change the
board identity, or relocate storage without checking the real device.
